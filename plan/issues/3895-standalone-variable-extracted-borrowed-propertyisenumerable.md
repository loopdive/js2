# #3895 — standalone: variable-extracted borrowed `propertyIsEnumerable` answers `false`

## Problem

In `--target standalone`, extracting `Object.prototype.propertyIsEnumerable`
into a variable before borrowing it makes it answer **`false` for a plainly
enumerable own property**:

```js
var o = { a: 1 };
var f = Object.prototype.propertyIsEnumerable;
f.call(o, "a"); // standalone: false   spec: true
```

The **inline** and **uncurried** spellings of the same operation are correct on
the same run, which is what isolates the defect to the extracted shape:

| shape                                                           | standalone | spec |
| --------------------------------------------------------------- | ---------: | ---: |
| `Object.prototype.propertyIsEnumerable.call(o,"a")` (inline)    |   **true** | true |
| `var f = …; f.call(o,"a")` (variable-extracted)                 |  **false** | true |
| `Function.prototype.call.bind(…)(o,"a")` (uncurried)            |   **true** | true |

Host is unaffected — it routes through `__proto_method_call` (see #3647).

## Measured

Harness: `runTest262File`, standalone lane, test262-shaped probe with controls
that must hold under any spec version. Base-4 probe code **2473** (`probe3` in
#3647's investigation), read as
`s1o=true, s1c=false, s2o=FALSE, s2c=false, s3o=true, s3c=false` — the `s2o`
digit is this defect. Identical before and after #3647's fix, so it is **not a
regression from that change**; #3647 touches only the host-side proxy.

Note the shape of the risk: because a class **method** is correctly non-enumerable,
the extracted form returns the *right answer for the wrong reason* on class
prototypes. It is only visible against a control — a plain own data property,
where `false` is unambiguously wrong.

## Root cause (located)

`src/codegen/expressions/calls.ts`, the `if (ctx.standalone && …)` borrowed-call
arm (~line 6962), matches the borrowed method **syntactically** on an *inline*
member chain (`Object` `.prototype` `.propertyIsEnumerable` `.call`). With the
method bound to a variable first, `innerExpr` is a plain identifier, the arm does
not fire, and the call never reaches `compilePropertyIntrospection`.

It then lands on the wasm-native helper `__propertyIsEnumerable`
(`src/codegen/object-runtime.ts:3081`), whose first act is
`ref.test $Object`. A statically-shaped object literal like `{ a: 1 }` compiles
to a **closed compiler struct**, fails that test, and the helper returns `0`.
The same structural reason makes `hasOwnProperty` suspect in this shape —
`__hasOwnProperty` is generated by the same `emitHasOwn` factory over the same
`$Object` predicate — so check it while you are here.

## Acceptance criteria

- `var f = Object.prototype.propertyIsEnumerable; f.call({a:1}, "a")` is `true`
  in standalone.
- The inline and uncurried shapes keep their current correct answers (assert all
  three shapes together so a fix cannot trade one for another).
- A control row that must hold under any spec version accompanies every
  assertion: a plain own property is enumerable; an absent key is not.
- Host lane unchanged — assert it, do not assume it.
- Cover `hasOwnProperty` in the same extracted shape, since it shares the
  `$Object` predicate.

## Notes

Two candidate directions, not yet chosen:

1. **Widen the recogniser** so a variable bound to a known
   `Object.prototype.<m>` is resolved to the same borrowed-call arm. Fixes the
   shape but stays syntactic — the next spelling escapes again.
2. **Make the native helper answer for closed structs.** `__propertyIsEnumerable`
   already receives a finalize-time prologue for closed-struct field names
   (`object-runtime.ts:6433`); the `ref.test $Object` early-return runs *before*
   it. Reaching the closed-struct arm before that return would fix every
   spelling at once, and is the more durable fix if the prologue can supply the
   enumerability bit as well as presence.
