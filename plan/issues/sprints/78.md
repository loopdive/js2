### What this wrap-up found

1. **Nine issues carried statuses no tool recognises.** Five read `complete` and
   five `in_progress` — neither is in the `SCHEMA.md` enum. `in_progress` is
   harmless (`build-data.js` normalises it), but **`complete` is not normalised
   anywhere**, and `freeze-sprint.mjs` matches `status === "done"` exactly. Left
   alone, five finished issues would have rolled forward as unfinished work,
   silently, every window. Four were verified done (their named verification
   suites are present and pass on main) and set to `done`; the fifth is #3764,
   below.
2. **#3764 is not done and was not marked done.** Its own suite,
   `tests/issue-3764-reference-array-oob-undefined.test.ts`, fails 2/3 on main:
   one failure is environmental (the test262 submodule is uninitialised here),
   but the other is real — the standalone-purity assertion
   `expect(result.importObject).toEqual({})` receives `env` plus a populated
   `string_constants`. It stays `complete` rather than being promoted on a
   status token alone.
3. **Every frozen window record read as still open on the dashboard.** Sprints
   75, 76 and 77 all had `isClosed=false`, because `build-data.js` falls back to
   `sprintNumber <= explicitlyClosedMax` for docs with no `status:` field, and
   the last doc carrying one was **74**. The rolling model stopped writing sprint
   frontmatter and nothing noticed. Adding `status: closed` to this doc raises
   the threshold to 78 and closes 75–77 with it.
4. **Generated sprint issue-tables had drifted and nothing heals them.**
   `sync-sprint-issue-tables.mjs` rewrote 16 sprint docs (+752 lines) — sprint 50
   was missing #1406, and so on. No GitHub workflow calls that script; it is
   npm/manual only. Unlike `npm-compat.json` or the test262 baseline, this
   artifact does **not** catch up on the next merge.

### Action items

- **Validate the status enum in CI.** Defects 1 and 2 both reduce to "no gate
  reads issue frontmatter against `SCHEMA.md`". A check that rejects any status
  outside the enum would have caught all nine at PR time, and is cheap next to
  the `check:issue-ids:against-main` gate that already walks these files.
- **Reconcile `SCHEMA.md` with practice.** The schema lists `review`; the
  lifecycle in `CLAUDE.md` and 17 live issues use `in-review`, and one issue uses
  `suspended`, which the suspend workflow writes but the schema omits. Pick the
  operative spellings and make the enum match before gating on it.
- **Decide whether `wont-fix` should freeze.** `freeze-sprint.mjs` moves only
  `done`, so the window's 11 `wont-fix` issues roll forward indefinitely, while
  the wrap-up skill's carry-over step treats `wont-fix` as terminal. The two
  disagree; the script is what runs.
- **Give the sprint-table sync an owner.** Either wire
  `sync-sprint-issue-tables.mjs` into a workflow or drop the generated tables —
  a generated artifact nothing regenerates is drift with extra steps.
- **Consider freezing on elapsed time as well as budget.** This window ran
  nineteen days and 783 issues before a `--force` closed it, because the trigger
  is budget-only and the budget signal is absent outside the statusline's host.
  Windows this size make every per-window number harder to attribute.
