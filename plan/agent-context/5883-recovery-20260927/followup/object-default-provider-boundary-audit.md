## Findings

1. Default identity preparation cannot be left to the current singleton finalizers. They call a builder which can register seeders and their closure/type dependencies after the companion dispatcher has already been filled. This is a concrete ordering hazard, conditional on a brand first entering that path late; it is not a measured failing fixture.
2. The native-first gate and singleton/seeder gates differ. A native-first JavaScript module without the opt-in native-regime environment flag can own native Objects but lack these standalone-gated providers. WASI has singleton reservation/fill but seeders remain standalone-only. No gate may be widened globally as an inventory-only change.
3. Boundary admission itself correctly avoids admitting raw Wasm objects. Nevertheless the same native open Object can be exposed as an identity-reversible host proxy whose prototype operations do not delegate to the native slot. This provides a concrete competing host backing-prototype route even without mixing compiler lanes.
4. Legacy host imports additionally write `_wasmStructProto` without checking native ownership. Passing a native carrier to a host-assisted consumer makes this a second potential native/host route. The import's behavior is source-proven; full cross-lane module transfer eligibility is not established by this audit and must not be claimed as an executed reproduction.

## Default-provider dependency proof

`object-runtime-prototype.ts:52–59,80–87` fills Object/Array singleton bodies using `buildLazyNativeProtoGetInstrs`. That builder (`native-proto.ts:405–445`) publishes a native singleton global and calls `ensureNativeProtoCompanionSeeder` during code generation, then may append a companion call. Seeder registration (`:688–730`) can defer until `__defineProperty_value` exists; pending brands flush at `object-runtime.ts:7068`. The registry is marked before recursive generation (`native-proto.ts:734–737`), but this is a recursion guard, not proof that all dependencies were present before a consumer snapshot.

Both current pipelines fill consumers first: `index.ts:6463` callable views, :6781 proto-index store, :6920–6921 Object/Array singletons; multi :11269, :11459, :11669–11670 respectively. `proto-index-store.ts:912,935` snapshots registered brands into force-create and seeder dispatch arms, resolving function names then. A brand newly registered in a later singleton fill will not appear in those already-emitted arms. `proto-function-value.ts:263,383,451` also chooses arms based on helpers present when it fills. Merely moving Object's finalizer earlier does not prove closure: seeding constructors/members can demand callable views and other brands recursively.

Gate details: `target-profile.ts:126–149` makes nativeRegime true for standalone or opted-in native-first GC/JS; `context/create-context.ts:419` assigns it to ctx.standalone. `object-runtime.ts:1071–1075` admits native-first JavaScript boundary operations independently of nativeRegime. Object/Array singleton reservation/fill uses standalone OR wasi, whereas `native-proto.ts:689` returns from seeder ensure unless standalone. Keep these distinctions explicit in the provider capability contract. Missing default is not actual null. Inventory cannot resolve this by enabling all seeders, changing protoMemberDirty, or emitting new bytes for unadmitted modules.

### Proposed encapsulation contract, not implementation authorization

- Separate **identity reservation**, **dependency preparation**, **body emission**, and **runtime initialization**. Reservation installs stable named handles/types/globals; it is not a write to an object's prototype and not proof that semantic support is active.
- Inventory default kinds before code changes: ordinary Object -> actual Object.prototype; boxed primitive -> its brand; callable-owned bag -> Function.prototype only at first owner association; generator bag -> captured factory link; intrinsic companion -> descriptor owner, not public identity; Object.prototype -> null; Array.prototype/class-root -> existing actual parent rules. Explicit null bypasses all defaults.
- Prepare the finite dependency closure during normal registration while imports/types may still be registered: Object and required brand identities, descriptor setters, closure/meta types, callable association helpers, proto-index companion reservation, brand seeders, then recursively demanded constructor/member brands. An already reserved handle breaks compile-time recursion; a reserved-but-unfilled body is not an executable null provider. Inventory the closure without broadening source admission or protoMemberDirty.
- Only after that closure is complete may consumer fills snapshot it. Fill callable views and companion dispatch against the frozen handles; singleton/default finalizers thereafter must be emission-only and must not register a new brand/helper/type/import. This requires splitting the current side-effecting builder or proving prior preparation makes its ensure calls inert. The latter is a verification obligation, not a guarantee from calling ensure twice.
- Resolve function handles at body construction after late-import shifts; use the normal defined-function APIs. Do not capture numerical indices before a preparation call that can add imports, subtract a later import count, reuse mutable Instr nodes, rebuild shifted bodies, or patch a stale body merely to hide an incomplete closure. Keep type/global handles in the existing context owner; inspect reindex boundaries before final fill.
- Runtime ordering already has useful guards: singleton global is stored before companion access (`native-proto.ts:405`), and companion is inserted in its table before seeding (`proto-index-store.ts:875–890`). Preserve both. Recursive Function/Object/constructor seeding must find the same identities. First-owner callable initialization must not overwrite explicit null or a prior relink; raw field null alone is insufficient (`proto-function-value.ts:457–478`).
- Both pipeline owners must place provider completion before B's final receiver hook and optimizer/DCE. Do not modify activation timing in this task. A complete reservation diagram still does not authorize deferred admission or retry.

## Concrete host routing and limits

### R1: native Object -> admitted host callback -> generic view -> same native Object

`runtime/boundary-object-adapter.ts:77–87` applies an admitted JS callable with converted this/arguments. `runtime.ts:11309–11324` supplies `_nativeBoundaryToHost` for this/argument conversion. That conversion (:8051–8053) sends a Wasm struct to `_wrapForHost`; the wrapper resolves decoder exports (:8898), uses a null-prototype JS backing object (:8958), and caches both directions (:9516–9519). Ordinary native open Objects take this generic path; their property read/write arms already recognize `__object_is_native_open` (:9201/:9225), but their prototype traps do not.

The generic view's getPrototypeOf trap (:9419–9429) returns a class mirror prototype or host Object.prototype while extensible, not the Object raw slot. No setPrototypeOf trap exists in this handler. Therefore host `Reflect.setPrototypeOf(view,p)` acts on the JS backing object's prototype; it does not commit the native Object slot. Returning the view passes through `_nativeDynamicFromHost` (:8013), which first unwraps it; `_hostProxyReverse` supplies the native identity (:9853–9867, subject to the foreign-mirror preservation rule). The admitted-object guard does not prevent these operations because the admitted target is the callback, not the native argument.

Source-level adversarial case for parent: native Object o has prototype p; admitted host function receives o's view, reads its prototype, sets a different q (or null), returns the same view; native code checks returned identity, prototype and inherited properties. The host backing target can hold q while native o still holds p; even the immediate host read can report the default instead of q. This is a source-traced competing state route, NOT an executed test result.

`preventExtensions` (:9477–9499) materializes and pins the host class/default prototype, then records `_wasmNonExtensibleObjs`; native Object integrity/prototype authority is not used by that prototype pin. This makes a simple added setPrototypeOf trap insufficient: once the view target is nonextensible, JS proxy invariants require its target prototype and reported prototype to agree. Subsequent native relinks must be impossible under the same authoritative extensibility state, or the view is unsound.

### R2: native raw receiver -> legacy host imports

Host-assisted Reflect lowering explicitly emits both `__host_set_struct_proto` and `__reflect_setPrototypeOf` (`expressions/call-namespace-static.ts:2703–2754`). The first handler (`runtime.ts:17021–17047`) accepts any detected Wasm struct and writes the global `_wasmStructProto` map; it does not ask the native-open discriminator or owning module. Host __getPrototypeOf (:15045–15088) prefers that map. The second handler (:15991–15995) wraps the receiver and changes the view backing prototype, independently of the map and native slot. The first write also precedes the second operation's success/failure; these are not a transaction.

Concrete routing condition: a native producer's Object arrives raw in a host-assisted consumer's externref argument, or a consumer unwraps a same-owner view. Neither host setter excludes it. Owner decoder support exists (`_decoderExportsFor`, :6466; `_wrapForHost`, :8898), but the legacy setter does not use it. Full admission/marshalling support for a chosen pair of compiler profiles still needs a parent-owned fixture; foreign mirrors can intentionally remain wrapped (:9865). Do not assume all linked transfers unwrap or that the consumer's structural Object test recognizes another module's layout.

### R3: genuinely host-owned values (keep this cut)

`_nativeDynamicFromHost` (:8044–8046) admits only non-Wasm raw objects/functions into the per-instance WeakSet; `_createBoundaryObjectImport` (:11308) checks that set. Thus the raw native Object is not directly authorized for host fallback by this path. Actual JS objects/proxies retain JS authority. A foreign identity-cached native view may be preserved by linking; classify it by recorded ownership, not solely typeof/_isWasmStruct on the view. Do not dismantle the admission guard or treat every externally seen object as native.

## Narrow ownership boundary specification

Keep native Object field+NULL_PROTO as the sole mutable link for a native Object. A host view is an identity adapter, not an independent semantic object. Use the owning module's existing decoder/identity records before the native-open discriminator. Parent/runtime owner inventories a minimal exported get-actual-prototype / try-set-prototype / integrity surface; do not call internal trusted stores directly from the host and bypass validation, status, cycle checks or proxy handling. Current export list (`object-runtime.ts:7001–7035` onward) exposes property MOP, not a demonstrated complete prototype authority bridge. Missing bridge is an integration blocker, not permission to fall back to `_wasmStructProto` for a known native owner.

Prototype proposals cross in exact semantic identity: reverse a known same-owner view to its raw carrier; preserve genuinely host objects/proxies, explicit null and foreign ownership. Return native prototype identities through stable host views. Do not substitute a property bag, constructor mirror, host Object.prototype or null merely because the native identity lacks a host adapter. In particular NativeProto singleton-to-host identity mapping must be inventoried before claiming default equality across the boundary.

For known native receivers, route generic view prototype get/set and host legacy Object/Reflect imports through that one authority; never also write `_wasmStructProto`. For legacy host-owned opaque carriers, retain their existing host owner until a separately authorized migration. For true JS objects use JS operations. Distinguish absent owner metadata from a definitive host-owned classification; unsupported owner delegation must not become an apparent successful set.

The host proxy backing object's prototype may exist as an invariant mirror only, never a competing semantic authority. Prototype and integrity operations need one coherent commit policy: preflight target invariant compatibility without executing duplicate user operations; commit via native status/writer with correct Object-throw/Reflect-false behavior; ensure the adapter cannot subsequently fail after the native write. If that cannot be proved with the current extensibility/descriptor mirror, boundary cutover is blocked. Do not solve it by blindly writing both stores or by rollback across observable effects.
