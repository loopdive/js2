# Goal: runtime-eval

**Runtime code evaluation — direct `eval`, indirect `eval`, and the `Function` constructor / `new Function` — works in both JS-host and standalone modes via a tiered fallback ladder, without embedding a third-party JS engine.**

- **Status**: Active (Tier-2 implementation is open; E6 provider packaging and official Test262 integration remain)
- **Track**: Parallel — the dynamic-code leg of the dual-mode architecture; does not block conformance goals.
- **Target**: `eval` / `new Function` produce correct results standalone, not an instantiation trap; the ~225 JS-host mechanism failures and the standalone dynamic-code cliff (roadmap §5) close.
- **Dependencies**: `standalone-mode` (the whole point is standalone dynamic code), `backend-agnostic-ir` (the IR→bytecode seam, #1713/#1715), `self-hosting-dogfood` (Acorn-via-js2wasm, #1710), plus in-flight substrate `#2864` (`$Frame`) and `#2527` (core-wasm linking).

## Why

`eval` and `new Function` are the last "deferred-feature" family treated as
wont-fix (skipped alongside `with`/Proxy in the IR fallback bucket). But they
gate a real test262 cluster and, more importantly, the dual-mode principle:
standalone modules currently **instantiation-trap** on any dynamic-code test
because the `__extern_eval` host import is absent. This goal finishes the
tiered ladder (compile-away → JS-host meta-circular → standalone interpreter)
so dynamic code has a Wasm-native answer, following the #679 (dual string) /
#682 (dual RegExp) dual-backend pattern.

The full design, strategy comparison, hard-problem answers, and test262
quantification live in
[docs/architecture/runtime-eval-interpreter.md](../../docs/architecture/runtime-eval-interpreter.md).

## Strategy (recommended)

A **tiered fallback ladder**, two rungs already shipped:

- **Tier 0 — compile-away** (#1163, shipped; broaden in #2923/#2924): constant
  strings spliced AOT. Standalone-safe today.
- **Tier 1 — JS-host meta-circular** (#1164, shipped; scope capture in #2925):
  recompile dynamic source through js2wasm at runtime.
- **Tier 2 — standalone bytecode interpreter** (#1584 strategy 2a; #2927/#2928/
  #2929): a WasmGC-native VM authored in the js2wasm-compilable TS subset and
  self-compiled, so its `JSValue` **is** the AOT `$Object` substrate — making
  the value-rep bridge free and preserving `ref.eq` object identity (the
  property the linear-memory QuickJS route cannot match).

## Convergence with `with` and Proxy

The interpreter substrate — environment reification (`$EnvRecord` extending
#2864's `$Frame`), the dynamic meta-object protocol, and the boxed-any bridge —
is the **same** substrate `with` and Proxy (#1355) need. The roadmap builds
these as shared primitives (see doc §7) so the tracks converge rather than
diverge. This goal does **not** own #1355/#2864 work; it coordinates carrier and
MOP-surface signatures with those owners.

## Success criteria

- `new Function("a","b","return a+b")(1,2) === 3` and `(0,eval)("1+2") === 3`
  both work in **standalone** mode (no JS host).
- Direct eval sees and mutates caller locals in both JS-host (#2925) and
  standalone (#2929), verified by a differential check.
- A no-eval module stays within 5% of the current size floor (optional linking
  via #2527); `with` exits the IR deferred-feature bucket.
- The interpreter's MOP primitives are consumed by at least one Proxy trap
  (#1355), demonstrating the substrate converged rather than duplicated.
