## manifestNeeds
What the frozen manifest would have to say to own this seam, and why the existing vocabulary does not fit as-is:

1. A GLOBAL-kind provider implementation. `RuntimeProviderImplementation` (src/ir/runtime-manifest.ts:450-522) has ten kinds; the only two that name a host/runtime *thing* are `host-callable { capability: RuntimeHostCapabilityFuncId }` (:485, typed on the FUNC half — `string.const` is a compile error there, and `#indexProviders` + `asCallableRuntimeHostCapabilityRecord` refuse it at runtime, pinned by the schema suite :561-600) and `runtime-callable { symbol }` (:493). Neither is a global. Needed: `host-global { capability: RuntimeHostCapabilityGlobalId }` (the host arm: the provider IS the import global whose field is derived from the literal by the record's scheme) and a native arm that is not a callable either — closest existing precedent is F2-S4's `carrier-field` (:508, "the first native arm in the catalogue that is not a callable"), so something like `native-global { role: "native-string-literal" }` naming the Program-ABI global ROLE (`PROGRAM_ABI_GLOBAL_ROLE.nativeStringLiteral`, program-abi-global-planning.ts:98), never a physical global index (the manifest freezes before `internNativeStringLiteral` allocates, and the index shifts).

2. A THIRD implementation for the oversized case: the native literal beyond ARRAY_NEW_FIXED_MAX=10000 is a `callable` (`__strlit_materialize_N`, minted per distinct literal, provider `irIntrinsicFuncRef(\"__ir_string_literal_materialize:N\")`, integration.ts:7388). That is per-literal, size-derived, and defined-function-shaped — `runtime-callable { symbol }` cannot name it because the symbol is minted, not fixed. Either the policy admits "native storage may degrade to a materializer" as a documented sub-arm of the native row, or the oversized case stays outside the manifest (recommended for slice 1).

3. Capability records: the two rows exist (runtime-host-capabilities.ts:301-302) and are already kind-discriminated with `field.scheme`; nothing new is needed on the record side EXCEPT that the record cannot enumerate fields — so any manifest projection that lists "requested capabilities" (`hostCapabilityRecords`) lists a scheme, and the per-literal field set (`string_constants.\"boot\"`) is only knowable from the demand scan. The manifest's demand for this feature is therefore a SET of literals, not a boolean — new shape versus every func-kind seam (which carry a boolean demand flag on the prepare input, intrinsic-support.ts ~:449).

4. Two features (the F2-S5 pattern), one policy: `js.string.const` (scheme literal) and `js.string.const.utf16` (scheme literal-utf16-hex); host rows name the two global capabilities, native rows name the native-global arm. The utf16 feature is NOT lane-selected: it is derived per literal by `hasLoneSurrogate` (imports.ts:175) inside the host arm, so a `StringConstPolicy { storage: \"host-global\" | \"native-global\" | \"unsupported\" }` selects the ARM and the utf16/literal split stays a provider-row (derivation) fact — exactly as F2-S5 keeps owned-append a row fact.

5. IntrinsicSignature: none fits. Every constant in src/ir/intrinsics.ts (:250-305: F64_TO_EXTERNREF, EXTERNREF_TO_F64, I32_TO_EXTERNREF, EXTERNREF_TO_I32, EXTERNREF_PAIR_TO_I32, F64_TO_U32, F64_UNARY, F64_BINARY) is a callable shape `params → result`. A global has no params and a VALUE type (`externref` on host, `ref $NativeString`/`ref $Utf8String` on native, both viewed through the string carrier). Either mint `EXTERNREF_GLOBAL_INTRINSIC_SIGNATURE` (`params [] , result externref`) purely nominally — as the native rows already reuse externref-pair signatures nominally for `ref $AnyString` helpers — or give global providers a `valueType` instead of a `signature` (a schema change to `RuntimeProvider`, :550/:592). The first is cheaper and consistent with F2-S3/S4.

6. Policy defaults per lane (frozen): gc-host → host-global; gc-native-strings / standalone / wasi → native-global (measured: 0 host string globals reached storageForConst on any native lane; the one host global minted under gc-native-strings, LATEGLOBAL, is a LEGACY producer through addHostStringConstantGlobal and never touches the IR seam); linear → DISABLED (its own data-segment plan, adapter does not consult the policy — same as eq/len/concat).

## risks
- The IR seam is NOT the minting authority in practice: 38 of 39 host-import mints in the 78 cells came from the legacy collector pre-pass (import-collector.ts:1671), and prepareStrings' own addStringConstantGlobal was `already:true` in 10/10 required-fixture host cells. A policy that 'decides storage' decides only the LABEL on a global something else already minted — the slice must state that plainly or it over-claims.
- When the IR path DOES mint (IR-only literals: boolean brand "true"/"false" in BOOLTPL — `already:false`), it does so AFTER module functions/globals exist (hasModuleGlobals=true, modFuncs=1) and triggers `fixupModuleGlobalIndices` once PER LITERAL (two fixups, thresholds 2 and 3, delta 1) because prepareStrings calls the single-value helper (:7314) not the batched one. A manifest-driven registration that changes WHEN these are minted (e.g. at freeze, before Phase 3) changes import ORDER (`string_constants."true"`/`"false"` currently trail every pre-pass global and the `wasm:js-string.concat` func import) and therefore the import-object shape and bytes.
- Import-section ORDER is a mixed product of three producers with three timings: collector func imports (env.console_log_string#0 BEFORE all globals in INIT; wasm:js-string.* likewise), collector literal globals at finalize in AST-scan order with string_constants16 INTERLEAVED (LONE: sc@0, sc16@1, sc@2), then late imports appended at their emission point (env.__concat_3 after the globals in TPLONLY; env.__throw_reference_error BETWEEN globals @2 and @3 in LATEGLOBAL). There is no single 'string globals then funcs' order to pin; a policy that sorts or groups by namespace would move bytes in every cell.
- The ordering hazard is real and live on the LEGACY path: LATEGLOBAL/gc-host mints `string_constants."n is not defined"@3` via addHostStringConstantGlobal from emitTdzCheckAtGlobal while `pendingInit` is TRUE, so `fixupModuleGlobalIndices(threshold 3, delta 1)` must walk the in-flight module-init body. The IR path is immune only because `resolveGlobal` (:6725) resolves the Program-ABI binding at emission; any slice that emits a raw `global.get <index>` for a manifest-selected global (instead of an IrGlobalRef) reintroduces #2043.
- gc-native-strings still mints a HOST externref global (LATEGLOBAL: `string_constants."n is not defined"@0`) because imports.ts:207 refuses only standalone/wasi/strict. A policy default of native-global for that lane must not be read as 'no string_constants import on that lane'.
- The oversized arm is per-literal and size-derived (LONG12000: 2 chunk globals + 1 defined helper, `funcIdx` a stable handle 2097203 resolved late). No manifest implementation kind can name a minted-per-literal defined function; forcing it into the policy makes the freeze depend on literal lengths.
- Two 'namespaces' but ONE lane arm: string_constants16 is chosen per literal by hasLoneSurrogate inside the host arm, and its runtime twin (src/runtime/string-constants.ts, runtime-instantiate.ts:25) must derive the identical key. The schema suite already pins the derivation; a policy must not offer utf16 as a selectable arm.
- Linear: `result.irOutcomes` is EMPTY on every linear cell; rejections (non-ASCII literal → ASCII proof required) surface only through getLastLinearIrReport(). A linear DISABLED policy row is safe, but any census that reads irOutcomes on linear will miscount.
- prepareStrings runs per pipeline (twice per compile when module-init is claimed; REGEX/gc-host showed two scans for [f] alone — unexplained). Policy freeze must be idempotent across those runs or the second run sees a different demand set.
- Pre-existing red: imported-string-constants (4) and issue-320 (1) fail on the unmodified tree because of the collector's function-name + "" globals (CLEAN cell: `"add"@0 ""@1` with no literal in source). Any slice PR will re-measure these as red; they are #5274's, not the slice's.
