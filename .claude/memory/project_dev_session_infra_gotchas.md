Two non-obvious infrastructure facts confirmed across a sprint-61 dev session (2026-06-12), both costing repeated debugging:

**1. Pushing a PR-revival branch to the `ttraenkler` fork.** Revival PRs (#1376, #1339) have their head branch on the `ttraenkler/js2` fork, and the `fork` git remote is HTTPS with NO stored credentials (`git push fork <branch>` → "could not read Username for https://github.com"). The `origin` remote (loopdive/js2wasm) uses an SSH deploy key that can't push to the fork. The working path is to push with the gh token embedded:
`TOKEN=$(gh auth token); git push --no-verify "https://x-access-token:${TOKEN}@github.com/ttraenkler/js2.git" <branch>`. Same trick for fetching a fork-only branch. For same-repo branches (pushed to `origin`/loopdive), `gh pr create` head is just `<branch>` (no `ttraenkler:` prefix) — the `--head ttraenkler:<branch>` form fails with "No commits between..." because the branch lives on loopdive, not the fork.

**2. `tests/helpers.js` is broken on main — use `tests/equivalence/helpers.ts`.** Many root-level `tests/*.test.ts` files `import { assertEquivalent } from "./helpers.js"` but `tests/helpers.js` does NOT exist (only `tests/equivalence/helpers.ts` does). So those suites fail at import on a clean checkout — a PRE-EXISTING failure, NOT caused by your change. When checking for regressions, always establish the baseline by running the same suite on a clean `origin/main` worktree before attributing failures to your diff. The real equivalence harness is `tests/equivalence/helpers.ts` (`compileToWasm`, `evaluateAsJs`, `assertEquivalent`) — write new issue tests under `tests/` importing `./equivalence/helpers.js`. It imports `vitest`, so probes must run under `npx vitest run`, not bare `tsx`. See [[feedback_baseline_drift_cross_check]].

**3. `WebAssembly.instantiate(binary, {env:{}})` stale-test failures are PRE-EXISTING, not regressions.** Many older unit tests (`class-method-calls.test.ts`, `externref.test.ts`, etc.) instantiate with an empty/literal import object. Since the lazy-`importObject` ABI change, compiled modules declare a `string_constants` import (and need `__setExports` wiring for closure dispatch via `__call_fn_method_N`), so those tests now fail with `Import #0 "string_constants": module is not an object or function` — on a clean `origin/main` too. The canonical harness pattern is: `const io = r.importObject ?? {}; const {instance} = await WebAssembly.instantiate(r.binary, io); io.__setExports?.(instance.exports);` then call exports. `compile()` is **async** (returns a Promise) and the result shape is `{success, binary, importObject, imports, errors, wat, exportSignatures}`. To prove no regression on a hot shared file, swap the original `closures.ts`/`runtime.ts` back in (via `git show origin/main:<f> > .tmp/orig`, cp, run, restore) and compare per-file/per-test failure counts — they should be IDENTICAL.

**4. A PR's `opened` event sometimes does NOT trigger `pull_request` workflows.** Observed 2026-06-14 on PR #1452 (loopdive/js2wasm): after `git push` + `gh pr create`, only the `pull_request_target` CLA Check ran — `ci.yml`, `test262-pr-stub.yml`, `test262-sharded.yml` never started, leaving the PR permanently BLOCKED ("required checks expected") even though it was correct. Fix: push an **empty commit** (`git commit --allow-empty`) to fire the `pull_request synchronize` event — all the `pull_request` workflows then run normally and go green. This is a GitHub transient, not a config bug. Watch for any PR stuck showing ONLY cla-check.

**5. Baseline pushes to `main` MUST use `MAIN_DEPLOY_KEY` (SSH deploy key), never `GITHUB_TOKEN`.** The `main` ruleset (loopdive/js2wasm ruleset 16700772) only bypasses GH013 ("changes must be made through a PR") for `DeployKey: always`. A `GITHUB_TOKEN`-authenticated push to `main` is rejected → silently freezes the committed test262 baseline → drift deadlock (regression gates go blind). All three baseline-promoting jobs use the deploy key + the `baseline-promote` Environment: `promote-baseline` (test262-sharded.yml), `sync` (baseline-summary-sync.yml), `merge-and-promote` (refresh-baseline.yml — fixed in #2149/PR #1452). If GH013 recurs, first confirm `gh api /repos/loopdive/js2wasm/rulesets/16700772 --jq .bypass_actors` still lists DeployKey.

**6. Merge-queue wedge handling (confirmed 2026-06-15).** Symptom: queue head sits in `AWAITING_CHECKS` indefinitely; the synthetic `gh-readonly-queue/main/pr-<N>-<sha>` branch EXISTS (group formed) but GitHub never dispatches the `merge_group` workflow runs. With `max_entries_to_build=5`, up to 5 groups build in parallel and can ALL wedge together.
  - **MONITORING GOTCHA (cost me a wrong diagnosis):** `gh run list --event merge_group` returns EMPTY even when runs exist. ALWAYS check via `gh api 'repos/loopdive/js2wasm/actions/runs?event=merge_group&per_page=20'` (the REST event filter). I misread the empty `gh run list` as "still wedged" and escalated prematurely.
  - **FIX LADDER — do NOT skip straight to the ruleset reset.** (1) `node scripts/unstick-merge-queue.mjs` (dequeue+re-enqueue the wedged head; `STALL_MINUTES=7` env to override the 12-min freshness guard when you have direct evidence). When it works, runs dispatch within ~1 min. (2) **AVOID the ruleset disable/re-enable "last resort"** — it can DEEPEN the wedge: a full disable/re-enable of ruleset 16700772 broke `merge_group` webhook dispatch ENTIRELY (dispatch worked ~1 min before the reset; dead for ~17 min after, defeating nudge + mass-nudge). (3) Recovery from a dead-dispatch state: **repeated push-to-main** revives it — admin-merge several green LOW-RISK PRs (docs/test/plan/tooling; classify by whether they touch `src/`) one at a time; the cumulative pushes rebuild all groups on fresh bases and dispatch resumes. Once revived, re-enqueue any codegen PRs and let the queue validate them properly instead of admin-bypassing.
  - `"Differential test"` is NOT a required check (not in ruleset 16700772's `required_status_checks`), so its failures never block a merge group. Required = cheap gate, merge shard reports, quality, equivalence-gate, check for test262 regressions, cla-check. (`smoke` is currently NOT required — an earlier add didn't persist.)
  - Editing ruleset 16700772 needs a full-body PUT (GET → modify → PUT); `PATCH -f enforcement=` 404s.
  - **Admin-merging multiple PRs that touch `plan/issues/` can introduce a DUPLICATE issue ID that the queue would have caught** (the queue rebuilds each entry on the latest main and re-runs `quality`). On 2026-06-15 admin-merging #1471 (renumbered treemap → 2155/2156) AND #1473 (assignment-lock filed as 2155) left TWO `id: 2155` files on main → the #1616 integrity gate ("N duplicate IDs") fails the required `quality` check in EVERY subsequent merge group → all queued PRs evict without merging → main silently blocked. Symptom to recognize: queue depth drops but `main` tip never advances, and `gh run view <CI-run> --log-failed | grep 'duplicate IDs'`. Fix: hotfix PR renumbering one of the colliding issues to a free id (keep coupled pairs together; renumber the lone single), `node scripts/check-issue-ids.mjs` to verify, then admin-merge the hotfix (plan-only PRs are path-filtered so they can't get the test262 required checks → admin-merge is the intended path). LESSON: when admin-draining during a queue outage, dedup the `id:` frontmatter across the batch first, or merge issue-file PRs through the live queue.
