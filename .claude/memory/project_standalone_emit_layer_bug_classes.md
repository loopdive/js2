Standalone codegen has TWO separate emit-layer failure classes that look similar ("invalid Wasm" / "u32 out of range") but live in different emitters. Distinguish by the ERROR PREFIX and the entry point:

1. **`Object emit error: ...`** → the relocatable object emitter `src/emit/object.ts` (`compileToObject` / `compileToObjectSource`, used for `.o` output). NOT exercised by `compile()`/`emitBinary` — so a bug here is invisible to plain `compile(..., {target:"standalone"})` + `WebAssembly.instantiate` smoke tests. To repro, you MUST use `compileToObject`.
   - Fixed instance (#2149, 2026-06-14): any/any `==`/`===` emitted `ref.test`/`ref.cast` with a NEGATIVE *abstract heap-type* typeIdx (`eq = -19`, `EQ_HEAP_TYPE` in `src/codegen/any-helpers.ts`). The object emitter unconditionally pushed an `R_WASM_TYPE_INDEX_LEB` reloc with `symbolIndex: typeIdx`, then `s.u32(-19)` threw. Fix: skip the type-index reloc when `typeIdx < 0` (abstract heap types are inline-encoded, not relocatable concrete types) for `ref.test`/`ref.cast`/`ref.cast_null` in `object.ts`. `ref.null` already had no reloc. `struct.*`/`array.*` always take concrete types (use `enc.u32`) so they're never affected.

2. **V8 `Compiling function #N failed: local.set[K] expected ...` / `call[K] expected ...`** at instantiation (the `@+offset` + `Compiling function #N` format is V8's). DESPITE looking like a binary-serializer bug, this is usually NOT in `src/emit/binary.ts` — it's a **stale funcIdx baked into a `call` before a late-import shift** (the late-shift hazard, class 3 below). emitWat reprints the `call` by NAME (always correct) while emitBinary writes the captured NUMERIC index (stale) → they "diverge". So an emitWat-valid / emitBinary-invalid module almost always means a codegen site captured a funcIdx too early.
   - Fixed instance (#2150 / TaskList #16, 2026-06-14): standalone `Array.prototype.indexOf/lastIndexOf/includes/filter/map` over an array-like receiver → `local.set[0] expected f64, found call externref` (search) / `call[0] expected extern` (filter/map). `compileArrayLikePrototypeCall`/`compileArrayLikePrototypeSearch` (`src/codegen/array-methods.ts`) captured `__extern_length`/`__extern_get_idx`/`__extern_has_idx` (+ `__host_eq`) funcIdx at the top, then compiled the receiver/callback/fromIndex (and filter/map registered `__js_array_*`) — each shifting defined-func indices, so the captured funcIdx was stale-low and the `call` hit the wrong function (indexOf's `__extern_length` resolved to `__object_keys` → externref into an f64 local). Fix: re-resolve the funcIdx from `ctx.funcMap` (names stable) AFTER the operand compiles, and pre-register the array-build helpers up-front. forEach/some/every/findIndex were fine because their funcIdx happened not to shift across the callback compile.

3. **Late-import / addUnionImports shift hazard** — see [[project_addunionimports_late_shift_hazard]]. Manifests as EITHER class-1 (`u32 out of range`, negative idx) or class-2 (V8 `expected X found Y`, wrong-function call). Rule: never capture a `funcIdx` into a JS const, then compile an operand / call `ensureLateImport`/`addUnionImports`/`ensureObjectRuntime`, then emit `call <captured>`. Re-read `ctx.funcMap.get(name)` right before the `call`, or register all late imports BEFORE resolving any funcIdx.

4. **SELF-shift hazard: a lazily-emitted helper function shifts its OWN captured funcIdx.** A `ensureFooFunction` that does `const funcIdx = ctx.numImportFuncs + ctx.mod.functions.length` (compute index up front), then emits the BODY, then `ctx.mod.functions.push(fn)` (push last) is buggy whenever the body lazily registers ANY other function (numeric-operator helpers like `%`→f64-modulo, coercion helpers, …): those append to `ctx.mod.functions` during body emission, so the real function lands at a position AFTER `funcIdx`, and every baked `call funcIdx` (the for-of driver, `.next()` dispatch, …) hits the helper instead. Caught in #2079 (Phase-2 standalone generators): `if (i % 2 === 0) yield i` → `call 52` resolved to `__f64_mod` ("not enough arguments on the stack"). **Fix: reserve the slot with a placeholder function pushed IMMEDIATELY after computing funcIdx** (`{name, typeIdx, locals:[], body:[{op:"unreachable"}]}`), emit the body (helpers append after the reserved slot), then fill the placeholder's `.body`/`.locals` in place — `funcIdx` stays stable. Same idiom as the accessor drivers (`src/codegen/accessor-driver.ts` `reserveAccessorGetDriver`/`fillAccessorDrivers`). This is distinct from class 3 (a caller capturing too early) — here the function's OWN emission self-shifts.

Debugging tip: to find a bad index, add a temporary `if (process.env.DEBUG_U32) console.error(...)` at `src/emit/encoder.ts` `u32()` (catches negatives). For a wrong-function call: print `funcIdx captured` vs `ctx.funcMap.get(name)` at the call site (if they differ → stale capture), and map "V8 func #N" → defined-func index N − importFuncCount, then read that function's typeIdx + name from the function/type sections. `compile()` does emitBinary AND emitWat from the SAME `mod`; if they disagree the bug is a stale captured index, not the serializer.
